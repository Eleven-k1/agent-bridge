2. 三类适配器统一的内部接口（提案）
三个适配器对上层完全同构，输入输出只有一套类型：

接口点	提案语义
invoke(request) -> ModelEvent 流	统一入口，永远流式；request 含模型名、消息数组、system、参数、超时、取消句柄、{task_id, run_id, agent_id, seq} 元数据
cancel(request_id)	幂等；已发取消后不得再产生业务 delta
probeConnection(config) -> ConnectionDiagnostics	连接测试；失败时返回错误类别+脱敏诊断，绝不含完整 Key
`listModels()	明确不支持`
能力元数据	流式、取消、用量统计、结束原因等，逐项声明支持与否
错误映射表	每家原始错误 → 统一 Error 类别（auth / rate_limit / timeout / network / protocol / server / cancelled / unknown），并标注可重试性
供应商差异只允许存在于适配器内部（请求体组装、流式解析、结束原因映射）；中转站返回畸形响应时归为 protocol 类错误并保留已收内容，不伪造结论。

3. 流式、取消、超时、错误的事件格式（提案）
先提案统一信封（需 M0 批准）：所有事件携带 event_id, task_id, run_id, seq, ts, type, payload。模型事件在此之上：

事件	关键字段	语义要点
model.stream.started	request_id	首 token 前发出
model.stream.delta	request_id, text_delta, index	顺序单调
model.stream.completed	request_id, finish_reason, usage	正常结束
model.cancelled	request_id, by(user/system/timeout), content_preserved	之后不得再出现 delta
model.timeout	request_id, phase(connect / first_token / stream_idle), elapsed_ms	超时分三段，让用户能区分“连不上”和“卡住了”
model.retry.scheduled	attempt, delay_ms, reason_category	有限重试可见
model.error	error{category, retryable, provider_message(脱敏), diagnosis_ref}	诊断引用指向日志，正文不含凭据
关键顺序语义：流式中断时，先入库并发出已收到的 delta，再发 error 事件（对应主方案 9.1“保留已收内容、不伪造失败模型结论”）。这条顺序约定本身也是需要写入 M0 的契约点。

4. Electron 与 Python 服务的通信边界
传输形态（提案）：回环地址 + 临时端口 + WebSocket 事件流，另有健康检查端点；会话令牌在 Python 进程启动时生成，仅经本进程私有通道交付给本 Electron 实例，不长期落盘。具体库由实施定，但边界不变。
方向规则：UI → Python 只有 Command（含幂等键 command_id）；Python → UI 只有 Event（统一信封、单调 seq）。UI 永远不接触 SQL、文件系统、Shell、模型 SDK。
门禁位置：审批与安全门禁只在 M3/M4 程序层执行；通信层不复制规则，但拒绝未鉴权连接（这是传输完整性，不是安全规则的前移）。
生命周期：Electron 负责启动与关闭；关闭顺序为停止收命令 → 取消进行中可取消操作并记录 → flush 事件 → 终止进程树 → 校验无残留。Python 崩溃时 UI 进入“服务不可用”态，不伪造完成。
版本协商：握手交换协议版本与能力，不兼容即阻止，不静默降级。

8. 断线、服务崩溃和协议不兼容时的界面行为
断线：全局状态条显示“与本地服务断开，正在重连（第 N 次）”；输入区标注“待恢复”，不清理已显示内容（那些是已入库事实）；重连后按补发事件刷新，发现序号空洞时明确提示“部分事件缺失”；暂停等命令不假装成功，只标“提交中”直至回执事件到达。
服务崩溃：与可重连断线区分开；显示“后端状态未知，以下为断开前最后已知状态”和最近稳定阶段；提供“重启本地服务”入口；重启后不自动重放任何命令、模型请求或审批，任务真实状态以 M5 恢复检查点为准，恢复选择权交给用户。
协议不兼容：握手失败即进入阻止页，展示双方版本、差异能力和升级指引；不提供“忽略继续”；禁止进入任务界面，防止旧字段被静默误用。
通用原则：这类界面状态本身就是对真实通道状态的反映，绝不显示“完成”。
9. 最容易发生的前后端不一致问题
按我判断的风险从高到低：

“完成”三义：UI 渲染完成 ≠ 编排阶段完成 ≠ 磁盘与测试真实完成。必须单一事实来源（task.state 事件），这也是职责书第 10 条的直接落点。
审批状态漂移：卡片还亮着，但后端已过期、被撤销，或经换主管/任务终止在别处被解决。需要 approval.resolved/expired 对所有解决路径可靠广播，UI 订阅全部路径。
流式中断的半消息：UI 已渲染的 delta 与后端入库记录不一致；或取消后缓存中的尾部 delta 又冒出来。取消事件后必须严格停止渲染。
命令假成功：断线时 UI 乐观更新了状态但命令未送达。对策：所有命令只标“提交中”，回执事件到达才变状态。
重连补发重复渲染：缺 seq 去重导致消息重复或乱序；UI 侧按 event_id/seq 幂等。
脱敏往返污染：设置页显示掩码，用户保存时把 sk-**** 当真值写回覆盖真实 Key。需要“掩码未修改则不更新凭据”的约定——这是接口语义，我会向 M3/M5 提交变更请求。
字段静默漂移：TS 类型手写、Python 端先行改动。用 M0 的 schema 一致性验证兜底，前端绝不手写字段名。
