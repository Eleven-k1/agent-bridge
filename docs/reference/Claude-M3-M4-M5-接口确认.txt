二、必须修改的阻塞问题
严重度标注含义：致命=不改则某条铁律退化为提示词级约束；高=不改则某个核心验收场景无法用记录断言。

B1（致命）CandidateEvent 缺摘要字段，与 §4 的校验语义自相矛盾。
行 69–79 的字段表里没有任何摘要字段，但行 101 要求 M5 "校验 event_deduplication_key 与候选事件摘要"，行 98 还允许返回 IDEMPOTENCY_CONFLICT。契约要求我校验一个契约没定义的东西。这就是我上一轮 A 问的字段，需正式补入：candidate_event_digest + digest_algo_version。语义必须写明：同键同摘要→幂等返回既有事件；同键不同摘要→DEDUP_CONFLICT 事实 + Blocker，禁止静默取首条或覆盖。摘要覆盖语义载荷，明确排除 event_id、task_event_sequence、observed_at/occurred_at、观测耗时与脱敏盐——否则每次正常重传都会因时间戳不同被误判为冲突，冲突信号当场失效。摘要须在脱敏之后计算，且由 M5 追加时重算校验，不能只信生产者。

B2（致命）STARTED 事实三处命名不一致，且无进程身份，孤儿回收不可实现。
行 54 列出 "STARTED、COMPLETED、FAILED、CANCELLED、RESULT_UNKNOWN"；行 138–142 的结果事件只有 TOOL_EXECUTION_COMPLETED/FAILED/CANCELLED/RESULT_UNKNOWN，没有 STARTED；行 339 又写成 "PLANNED、COMPLETED、FAILED"。三处指的是同一件事还是三件事，无法判断。
更关键的是：PLANNED 时进程尚未启动，因此不含 pid；RESULT 在崩溃时不存在。中间缺一条已落盘的"已启动"事实携带进程身份（pid + 进程创建时间 + Job 标识），异常退出后我无法安全回收孤儿进程——只有 pid 会因 pid 复用误杀无关进程，没有 pid 则完全无法定位。这直接使规则 8（取消后清理进程树）与 §18.8 通过条件"本地 Python 服务和子进程没有失控残留"不可实现。必须：统一命名，并新增携带 ProcessHandle 的启动事实。

B3（致命）canonical_action_digest 未按 operation_kind 定义，命令类操作留有后门。
行 172、181 只给出通用的"目标、参数、路径、哈希"。对文件类够用，对命令类不成立。命令类必须绑定：解析后可执行文件的真实路径及其自身哈希、argv 数组指纹、cwd、环境变量指纹，以及——当命令是脚本入口（npm test、pytest 配置入口）时——被执行脚本内容的哈希。
不绑脚本内容的后果很具体：用户批准 npm test 之后，执行者改写 package.json 的 scripts 段，同一条命令、同一个摘要，执行的却是任意代码。审批看起来完好，实际已被绕过。这条不补，规则 3（危险操作绑定具体票据）在命令类上形同虚设。

B4（致命）workspace_identity 只写"规范化识别"，唯一租约不变量可被别名打破。
行 16 与行 188 均未要求身份包含卷序列号 + 文件 ID。若身份取自用户输入的路径字符串，则 D:\proj 与经 junction 指向同一目录的 D:\link 会被判为两个工作区，各授一个租约，同一批文件出现两个写入者——行 204 的不变量被绕过而不被检出。必须要求：workspace_identity 由解析全部 reparse point 后的真实路径 + 卷序列号/文件 ID 构成。同时缺嵌套工作区规则（工作区 B 位于已打开工作区 A 之内），契约层需能表达，不能留空。

B5（致命）无基线状态机，租约授予前置条件不含基线就绪。
phase 有 EXECUTION_PREPARING，但没有任何基线状态；行 199–201 的授租前置也不含基线。于是非 Git 项目可以在没有可恢复基线的情况下取得写权限，规则 11（非 Git 项目必须先建立可恢复基线）只剩文字约束。必须新增 BASELINE_REQUIRED → BASELINE_CREATING → BASELINE_READY | BASELINE_FAILED，并把 BASELINE_READY 设为非 Git 工作区授租的硬前置。

B6（致命）Evidence 等级 1 的生产者未限定，技术证据可被伪造。
行 26 定义 Evidence 由 M0 定义、M5 保存；行 309 等级 1 是"测试、命令、文件哈希、Diff、Git、进程事实"；行 313 等级 5 是模型意见。但契约没有规定谁有资格产出等级 1。模型输出经 M1/M2 提交时若能标注为等级 1，主方案第 8、9 条铁律（不得把模型口头结论当证据）就无法程序强制。必须写明：等级 1 只能由 M4 观测事实或 M5 存储事实支持，并携带 operation_id 与命令指纹；M1、M2、M7 不得声明等级 1。

B7（高）快照区被归入"临时执行区"，且未区分两类文件写入者。
行 32 把 M5 正式审计区之外的部分统称"临时执行区，具体实现不属于 M0"。这有两个问题。其一，非 Git 基线快照不是临时数据——它是规则 11、规则 12 与 §18.7 三级恢复的依据，需要完整性保护与恢复语义，不能划到契约之外。其二，也更重要：契约层必须区分内部存储写入通道（M4 写快照内容、大输出 blob、子进程重定向 tmp）与模型可调用的文件工具。后者必须把整个 .multi-agent/ 视为拒写。若二者共用一个工具定义，执行者就能请求往审计区写入，进而篡改事件日志、检查点与恢复基线——这是我上一轮列的第 3 号越权风险，也是行 32 目前唯一没有堵住的口子。

B8（高）恢复语义与检查点稳定性判据不完整。
三处缺口：其一，RECOVERY_REQUIRED 无 reason 枚举（至少须区分"审计保存失败"与"副作用结果未知"，二者对账方式不同）、无未对账操作清单；其二，最现实的触发原因是磁盘写满，而磁盘写满同时会让"记录进入 RECOVERY_REQUIRED"这次写入也失败，行 151 承认了持久化可能不可用，但没有规定降级标记通道；其三，Checkpoint 虽已定义为"证据引用"（行 25，符合我上一轮的要求），但缺一条判据：存在已 PLANNED 而无 RESULT 的操作时，该检查点不得标记为稳定，须携带未对账操作清单。缺这条，"最近稳定阶段"会把一个可能已改磁盘的时刻声称为稳定。

B9（高）workspace_change_state 三态不足，且用户既有未提交修改无契约位置。
行 253–256 只有 NO_TASK_CHANGES/TASK_CHANGES_UNVERIFIED/TASK_CHANGES_VERIFIED。TASK_CHANGES_UNVERIFIED 隐含"我知道改了什么、只是没验证"；但在 RESULT_UNKNOWN 或外部冲突之后，变更集本身未知，这两种情况在契约上无法区分。需要"变更集未对账"态。
另外，主方案 §7 行 182 与 §18.1 通过条件都要求区分"原有未提交修改"与"本任务修改"，而契约里没有承载"任务开始时已脏文件集合"的位置。没有这个基线事实，我做 git add 精确路径清单时无法用记录证明"原有修改未被混入本任务提交"，§18.1 该条通过条件不可断言。

B10（高）票据消费的原子性未要求，取消失败与部分恢复无法表达。
行 177 有 remaining_uses、行 180 有"已消费"，但没有一条像行 201 那样规定消费必须是权威端的不可分割操作。租约有原子保证、票据没有——并发或重入下 remaining_uses 可能超额扣减，规则 4（一次审批不扩展）在阶段同类批准上出现缺口。票据消费与租约授予应在同一权威端具备同等原子语义。
同时，两个真实结果无法表达：进程杀不掉时（行 285 "安全终止"未定义失败情形），把状态记成 CANCELLED 就是记录失真，需要"取消失败仍在运行"的独立结果；恢复操作部分成功时（部分文件被占用），只能记成 COMPLETED 或 FAILED，前者掩盖未恢复项、后者掩盖已改动项，需要"部分完成"的表达。

B11（高）ContextManifest 未区分"已批准待发送"与"实际已发出"。
行 317–322 的责任链已定（M1 选择 → M3 阻止或脱敏 → M1 形成清单 → M5 记录 → M2 传输），生产者归属问题解决，且 M5 记录在 M2 传输之前，写前纪律正确。但仍缺三件事：批准之后可能因取消、崩溃或供应商报错而根本没发出，混同会让审计声称"某个敏感文件已发给某模型"——既失实又无法反驳；一次批准可能对应多次重试发送，需要计数；§18.5 要断言"未经专门批准不发送原文"，这只能靠实际发送记录证明，批准记录证明不了。
最小事件语义（只给语义，不涉数据库实现）：ContextSelectionRecorded（纳入项含路径+内容版本+理由，排除项含命中规则）、SensitiveFindingRecorded（规则 id、位置、严重度、处置为 BLOCKED/REDACTED/ALLOWED_BY_TICKET、占位符 token，永不含原文）、ContextSendApproved（票据、目标模型、Base URL 脱敏身份、允许形态、最大次数、过期）、ContextSendAttempted（必须在网络调用之前落盘，含发送 id、载荷摘要、条目引用、字节数）、ContextSendOutcome（DELIVERED/FAILED/CANCELLED/UNKNOWN）。
必须写进契约的两条规定：UNKNOWN 结果按不对称处理——安全核算上按"数据已离开本机"计，任务逻辑上按"未送达"计；ContextSendAttempted 对非敏感上下文同样发出，否则主方案 §6.6 要求的"记录各智能体实际收到的上下文和文件版本"追溯不到具体请求。

B12（中高）读取基线与租约世代未绑定。
行 205 允许无租约读取，这本身合理。但冲突检测的基准版本是在读取时登记的，而契约没有要求"写入时校验该基准是在同一 lease_id + generation 下登记的"。换执行者后，新执行者可能基于前任读到的文件版本产出修改，落盘时磁盘哈希恰好未变、校验通过，但修改内容是针对一个它从未读过的版本计算的。建议：写入时要求基准登记与当前租约世代一致，不一致则强制重读。

五、必须补充的契约测试
在 §15 已有 18 条之外补充。契约层部分由 M0 负责人实现，我提出要求；M3/M4/M5 部分由我实现，结论按规则 14 由非作者复核。

契约层：

同键同摘要幂等无操作；同键异摘要产出 DEDUP_CONFLICT，且不得静默取首条或覆盖（行 101/98 目前无对应测试）。
Python 与 TypeScript 两侧对同一事件计算出相同摘要（跨语言规范化一致性）。
正常重传因时间戳差异不得被判为摘要冲突。
存在 PLANNED 无 RESULT 时构造 Checkpoint：不得标记稳定，必须携带未对账清单。
Checkpoint 内嵌事实值（而非引用）应不可表达。
M1/M2 提交等级 1 Evidence：应被拒绝。
明文凭据进入任何持久化事件载荷：应被拒绝（对应行 305 的行为规则）。
结果为 RESULT_UNKNOWN 的操作触发自动重试：应被拒绝。
M3/M4/M5 侧：

租约并发授予：并发两次只有一次成功；旧 generation 的延迟写入被拒；换执行者无重叠窗口；第二个应用实例无法授租；junction 别名指向同一目录时不得授出第二个租约（对应 B4）。
票据原子性：并发消费不超额扣减 remaining_uses；阶段同类批准不越出路径前缀、次数与时间上限；重启后全部失效；内容漂移导致的失效可与普通过期区分。
执行前二次校验 TOCTOU 四例：审批与执行之间替换 junction、替换文件、改内容、改 package.json scripts，均须在落盘前被拦（第四例对应 B3）。
孤儿回收：pid 复用场景下进程身份不匹配须拒绝回收而非误杀（对应 B2）。
崩溃注入六点：讨论中、等审批中、已改未验证、命令执行中、结果落盘瞬间、快照创建中途；每点检查恢复行为、租约失效、票据失效、无自动重放、无进程残留。
存储写失败注入：磁盘写满时仍能进入并标记 RECOVERY_REQUIRED；截断记录被检出并标记缺口而非静默补齐（对应 B8）。
基线门禁：非 Git 工作区在基线就绪前申请租约必须失败（对应 B5）。
模型可调用文件工具请求写 .multi-agent/：必须被拒绝，且 M4 内部快照通道不受影响（对应 B7）。
Git 既有修改保护：任务开始时已脏文件不进入本任务提交路径清单，可用记录断言（对应 B9）。
取消失败：进程不可终止时状态不得记为 CANCELLED（对应 B10）。
恢复部分完成：部分文件被占用时，已恢复与未恢复项都能从记录还原（对应 B10）。
ContextManifest：批准未发送不得呈现为已发送；发送结果 UNKNOWN 时安全侧按已发出计、任务侧按未送达计（对应 B11）。
敏感信息矩阵：假 .env、假私钥、假 Token、证书、连接串、命令行内 token、环境变量快照、Git 输出、异常堆栈，均不得出现在模型请求、事件、日志、报告与导出包。

六、最终结论
有条件确认。

v0.3 的模块边界与 M3/M4/M5 相容，我在本轮审查中没有发现任何要求我跨界修改公共协议、编排器、模型适配器或前端的地方；你列的 10 项语义方向全部可实现。因此不是"不可确认"。

条件是第二节 B1–B12 得到处理（采纳，或由 M0 给出等效表达）。其中 B1、B2、B3、B4、B5、B6 属致命项：不处理则规则 3（危险操作绑定具体票据）、规则 7（唯一写入者）、规则 8（取消后清理进程树）、规则 11（非 Git 先建基线）以及主方案第 8、9 条证据铁律，会退化为提示词级约束——这正是明确禁止的形态。B1 与 B3 尤其要强调：前者是契约内部自相矛盾（要求校验一个未定义的字段），后者是一个可被实际利用的审批绕过路径。
